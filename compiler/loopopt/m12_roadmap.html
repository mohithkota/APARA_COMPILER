Milestone M12 · Research Design (no implementation)

What to build next — a measured roadmap to higher IPB

The M0–M11 framework is complete, integrated, and evaluated. M11 showed the compiler reaches only ~1.8 instructions per bundle on an 8-lane machine — and pinpointed exactly why. This is the evidence-driven plan for the next phase: which techniques attack the measured bottlenecks, which fit the existing LoopTransform framework, and the order to build them in.

Thesis. The limiter is not the hardware and not the scheduler — it is a lack of independent work inside each scheduling window. ILP-saturation is ~0% and register pressure peaks at 5 of 28: the bundler almost never runs out of lanes, it runs out of things to put in them. The winning strategy is therefore to expose parallelism at the IR level and let the existing greedy bundler pack it — which is exactly what the LoopTransform framework was built to do.

1 · Bottleneck → root cause → required technique

Three causes account for >99% of every lost bundle slot
largest
58%

True data / recurrence dependencies

Why: dependent instructions in one iteration cannot co-issue. Independent work exists only in other iterations — invisible to a within-block packer.

Why we can't fix it now: no pass overlaps iterations; the bundler never crosses the back-edge.

→ software pipelining · unrolling
second
21%

Memory dependencies

Why: the bundler must assume two memory ops may alias, so it serializes them (MemAlias/MemPhase).

Why we can't fix it now: M2 has alias facts, but the text-level bundler can't consult them; its disambiguation is conservative.

→ memory disambiguation · dependence graph
third
20%

Control-flow boundaries

Why: a branch, call or label ends a bundle. The scheduling window is one basic block.

Why we can't fix it now: the bundler is basic-block-local; nothing enlarges the region or removes small branches.

→ if-conversion · global scheduling

Hardware-lane limits (0.6%) and ILP-saturation (0.0%) are negligible — decisive evidence that the machine has spare width and the problem is upstream of the scheduler.

2 · Framework readiness — the strategic split

Restructure in the IR (native); schedule in the bundler (harder)

The LoopTransform framework is an IR-level, loop-scoped, transactional rewrite engine with verification and rollback. Instruction placement happens later, in the greedy text-level bundler. That divides every candidate cleanly:

Class A — framework-native

  • Expose ILP by rewriting loop IR; the existing bundler then packs the newly-independent work.
  • Unrolling, software pipelining (emit prologue/kernel/epilogue as IR), if-conversion, unswitching, fusion/fission, register promotion, vectorization.
  • Uses M0–M4 analyses, M7 legality, MutationTransaction (splice / move / replace_span), verification + rollback — no new engine required.

Class B — scheduler-level

  • Control actual placement or cross block boundaries.
  • Global / trace / superblock scheduling, true modulo reservation scheduling, predicate lane assignment.
  • Needs a new scheduler or bundler surgery — largest architectural risk.

Key design choice: most of software pipelining's benefit is reachable in Class A — emit an already-interleaved kernel as IR and let the greedy bundler pack it, using the MII that M3 already computes. This avoids building a Class-B scheduler up front.

4 · Proposed research milestones

R1–R6, sequenced by dependency and de-risking

  1. Loop Unrolling

    Class A · effort LOW · expected IPB: large on hot loops
    Objective
    Full/partial unroll of counted loops (with a remainder loop) to expose several independent iteration bodies to the bundler and cut back-edge/control overhead.
    Dependencies
    M1 (trip counts, IV rewrite), M3 (pick factor by body size / register headroom), M7 legality, MutationTransaction.
    Deliverables
    LoopUnroll(LoopTransform); factor-selection heuristic; remainder-loop synthesis.
    Validation
    Differential golden test vs gcc on the corpus (see cross-cutting harness); framework verifier + rollback; re-run M11 to measure IPB/occupancy delta.
    Success
    Measurable rise in mean lanes/bundle and drop in single-lane bundles on loop-bearing programs, zero correctness regressions.

  2. Dependence Graph & Memory Disambiguation

    analysis milestone · effort MODERATE · unblocks 21% + enables R4
    Objective
    A reusable data-dependence graph (register + memory, with distances and latencies) and a strengthened alias oracle that proves independence for IV-indexed and distinct-base accesses.
    Dependencies
    M1 (IV-based address characterization), M2 (extend MemEffects/AliasSummary), M3 (already builds recurrence/critical-path structure — reuse).
    Deliverables
    DDG analysis in the M-analysis idiom (annotate descriptors); disambiguation results plumbed to the scheduler/bundler; cross-check that it never claims false independence.
    Validation
    Conservative-soundness audit (never fewer edges than the safe baseline); precision report vs the current bundler alias check.
    Success
    Provably-sound DDG available to later passes; measured reduction in MemAlias-forced splits where aliasing is disproved.

  3. If-Conversion / Predication

    Class A · effort MODERATE · attacks 20% control · enables R4
    Objective
    Convert small in-loop if-then(-else) into branch-free $cmov straight-line code, removing control boundaries and making such loops pipelineable.
    Dependencies
    M2 (safety: no un-speculatable stores/calls — eased by the fault-free VM), M3 (profitability), M7, existing $cmov lowering.
    Deliverables
    IfConvert(LoopTransform); profitability gate; interaction with R1/R4.
    Validation
    Golden differential test; verifier; A/B IPB on control-heavy loops.
    Success
    Fewer control/label splits on eligible loops; no regression where if-conversion is unprofitable (gated off).

  4. Software Pipelining via Swing Modulo Scheduling

    Class A (IR-emitted kernel) · effort HIGH · the flagship attack on 58%
    Objective
    Overlap iterations at the Minimum Initiation Interval M3 already computes: emit prologue / steady-state kernel / epilogue as IR so the greedy bundler packs the independent cross-iteration work.
    Dependencies
    R1 (unroll/kernel infrastructure), R2 (DDG + latencies), R3 (for loops with control), M3 (res_mii/rec_mii/mii/est_ipb as the schedule target and ceiling).
    Deliverables
    Swing modulo scheduler; modulo reservation table honouring the 4 ld/st + 1 div/sqrt lane limits; kernel register handling; SoftwarePipeline(LoopTransform).
    Validation
    Golden differential + simulation on pipelined kernels; per-loop achieved-IPB vs M3's est_ipb ceiling; tiered fallback to the unpipelined loop on spill/verify failure.
    Success
    Loop IPB approaching est_ipb on resource-bound loops; recurrence-bound loops correctly capped at rec_mii; zero correctness regressions.

  5. Global / Superblock Scheduling

    Class B · effort HIGH · crosses the 20% control boundaries
    Objective
    Form single-entry regions along hot paths and schedule across block boundaries (with compensation code), reaching the control-flow-bound code that R3 can't predicate.
    Dependencies
    R2 (DDG), M3 (edge/loop profile for region formation), the fault-free VM (cheap speculation).
    Deliverables
    Superblock formation; a region scheduler feeding the bundler; compensation-code insertion.
    Validation
    Golden differential; verifier extended for multi-exit regions; IPB on control-heavy, non-loop code.
    Success
    Higher occupancy in straight-line-poor code without correctness loss.

  6. Vectorization (APARA vector ISA)

    Class A · effort HIGH · research-novel, narrow but deep
    Objective
    Map stride-1 data-parallel loops onto the native $v/$dot/$vreduce vector ops (vu8_t), collapsing whole scalar loops into a few instructions.
    Dependencies
    R2 (no loop-carried deps proof), M1 (stride), alignment analysis (new), the existing vector ISA.
    Deliverables
    Vectorize(LoopTransform); alignment/remainder handling; cost model.
    Validation
    Golden differential; the existing vector-intrinsic tests as regression anchors.
    Success
    Data-parallel kernels lowered to vector form with large instruction-count reduction, correctness preserved.

6 · Risks

What could go wrong, and where
high

Correctness of new semantics

Unlike M6–M10, new optimizations have no legacy byte-diff oracle, and the M5 verifier checks loop structure, not data-flow equivalence. A dedicated differential-correctness harness (gcc golden + simulation) is a prerequisite, not an afterthought.

high

Scheduler complexity

Modulo scheduling is the hardest classical algorithm; a wrong kernel/prologue/epilogue silently miscompiles. Mitigate with the IR-emitted-kernel design and tiered fallback.

med

Register pressure

Unrolling and pipelining lengthen live ranges. Headroom is real today (peak 5/28), but deep kernels can spill; the existing tiered-fallback codegen contains the blast radius.

med

Compile-time growth

The framework rebuilds analyses after every transform; modulo scheduling is expensive. Large programs already reach tens of ms — watch for super-linear growth and cache analyses across a transform's attempts.

med

Pass interaction

unroll × if-convert × pipeline ordering matters; the tiered pipeline mitigates but tier count grows combinatorially.

med

Analysis-to-bundler plumbing

The bundler is text-level; IR-derived alias/schedule facts must reach it. Prefer the "emit already-scheduled IR" path to avoid deep bundler surgery.

7 · If I had another year — first, second, third

The three-move plan, each justified by M11
First

Loop Unrolling

Lowest effort, highest framework fit, and it directly converts the 57%-single-lane reality into multi-lane bundles by handing the greedy bundler independent iteration bodies. Register headroom (5/28) means we can afford it. It is the substrate every later pass builds on, so it de-risks the whole roadmap.

Second

Dependence Graph + Memory Disambiguation

The 21% memory bottleneck is real, but more importantly a sound DDG is the required foundation for any reordering or pipelining. Building it second means the flagship pass lands on solid ground instead of conservative guesses.

Third

Software Pipelining (Swing Modulo Scheduling)

The direct attack on the dominant 58% true-dependency bottleneck and the single largest IPB lever. M3 already computes the MII target and ceiling; unrolling (first) and the DDG (second) make it tractable. Highest payoff, correctly sequenced last of the three.

8 · Long-term compiler vision

From a greedy packer to a dependence-driven pipelining VLIW compiler
Today the compiler is a local greedy bundler fed by loop restructuring. The endgame is a dependence-driven, software-pipelining VLIW compiler: IR-level transforms (unroll, if-convert, pipeline, vectorize) expose iteration- and region-level parallelism; a modulo scheduler places it at the Minimum Initiation Interval; the fault-free VM is exploited for cheap speculation; and every transform rides the M5 transactional framework with a differential-correctness net catching what the structural verifier cannot. The measurable north star is already defined by M3: drive each loop's IPB from today's ~1.8 toward the est_ipb ceilings the profiler computes — closing the gap the M11 evaluation made visible.
