# REPRODUCIBILITY

Everything reported in `R5_0_FINAL_EVALUATION.md` and `R4_6_5_EVALUATION.md` is
regenerated by one command, with no manual intervention.

## Requirements

| dependency | version used | notes |
|---|---|---|
| Python | 3.12.3 | any 3.8+ should work; f-strings and `dataclasses`-free code |
| pycparser | 3.00 | the **only** third-party package |
| git | 2.43.0 | for artifact verification only |

**No numpy, no matplotlib, no pandas.** Figures are emitted as hand-written SVG
and ASCII so the artifact has no plotting dependency.

```bash
pip install pycparser
```

## Regenerate the entire evaluation

From the repository root:

```bash
python3 compiler/evaluation/__main__.py
```

Runtime ≈ 5 s. It prints the full report and writes:

```
  compiler/evaluation/results/
    benchmarks.csv           one row per benchmark, every raw metric
    summary_by_family.csv    per-family means
    gap_analysis.csv         lost slots per cause
    gap_detail.csv           lost slots per benchmark (audit trail)
    report.txt               the printed report
  compiler/evaluation/plots/
    coverage.svg
    dynamic_reduction.svg
    ipb_per_benchmark.svg
    ipb_scalar_vs_vector.svg
    oracle_comparison.svg
    gap_causes.svg
    ipb_distribution.txt
```

Every table and figure in the evaluation reports derives from
`results/benchmarks.csv`; nothing is transcribed by hand.

## Determinism
Every reported metric is deterministic. Verified by diffing
`results/benchmarks.csv` across two consecutive runs: **the only column that
differs is `compile_seconds`** (wall-clock timing). All counts, IPB figures, gap
percentages (74.0 / 14.6 / 8.8 / 2.6), decisions and realisations are bit-stable,
because the vectorizer resets its fresh-temp and label counters per module, so
emitted names — and therefore generated code — are identical across runs.

Consequence for reviewers: re-running the harness will reproduce every table and
figure exactly; only the compile-time column will vary with machine load.

Expected: 13 × `ALL … TESTS PASS`, 8 × `RESULT: PASS`, and
`RESULT: PASS` for the crosscheck (124/124 identical).

Total runtime ≈ 15 minutes; the corpora dominate because each compiles the
124-program regression set.

## Compile a single program

```bash
python3 compiler/compiler.py program.c -o program.mcode -v
```

Useful environment switches (all default to *enabled*):

| variable | effect |
|---|---|
| `APARA_NO_VECTORIZE=1` | disable all vectorization |
| `APARA_VECTOR_REALISATION=unrolled\|compact\|unrolled+peeled\|compact+peeled` | force one realisation |
| `APARA_VECTOR_COMPACT_MARGIN=<float>` | acceptance margin for a non-incumbent realisation (default 0.10) |
| `APARA_VECTOR_FAST_PROBE=1` | use the cheap pre-optimizer size probe |
| `APARA_NO_SWP=1`, `APARA_NO_SUPERBLOCK=1` | disable R3.1 / R3.2 |
| `APARA_VECTOR_REPORT=1` | print the R4.0 capability report (with `-v`) |

## What is *not* reproducible here
- **Hardware or cycle-accurate simulation.** The project's validation policy is
  IR-level; dynamic operation counts come from the vectorizer's model, not a
  simulator run. Reproducing *measured* cycle counts would require the APARA
  toolchain (`mcode_align`, `mcode_assemble`, `mcode_run`), which is external to
  this repository.
- **The 124-program regression corpus** lives under `testing/`,
  `new_isa_tests/`, `demo_prof/` and `isa_coverage_tests/`; the corpora scripts
  discover it by glob. Generated build artifacts there are git-ignored and are
  recreated by running the compiler.
